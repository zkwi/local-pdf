# 后续方向

按「收益 / 代价」排序，不是承诺。

## 值得做

1. **页面诊断预览**
   把 PDF 渲染出来，叠加识别出的区域、栏边界、表格网格。三层 IR 里已经带了
   `sourceElementIds`，数据结构不用改，只差一个画 overlay 的组件。
   这也是所有版面算法调优的基础设施。

2. **用户手工修正**
   手动指定栏数、拖动调整区域顺序、框选表格区域、框选 OCR 区域。
   PDF 的任意版式没法靠规则全自动判准，**让用户改一两个区域，往往比无限堆启发式更有效**。

3. **无框线表格**
   `ConvertOptions.detectBorderlessTables` 现在是占位（不生效）。真要做，依据是：
   多行稳定的 X 对齐簇、列间空白、行间距规律、数字/文本的对齐形式。
   阈值必须设高——低置信度时宁可输出成多个对齐段落，也不要生成错误表格。

4. **文字颜色**
   pdf.js 的文本接口不带颜色。要拿到得在遍历操作符列表时把 `setFillRGBColor`
   和 `showText` 的顺序对齐，工程量不小。

5. **批量输出 ZIP**
   现在"下载全部"是逐个触发下载。加个 zip 打包更顺手（需要引入一个 MIT 的 zip 库）。

## 想清楚再做

6. **高保真模式**
   浮动文本框 + 固定定位。视觉接近但编辑体验差，且 Word / LibreOffice / OnlyOffice
   对浮动对象的处理差异不小。建议先做完诊断预览，看真实需求再定。

7. **中文 OCR 换模型**
   Tesseract 的中文识别对复杂排版和表格一般。可以加一个 ONNX Runtime Web 适配器
   评测 PaddleOCR 系列。`OcrEngine` 接口已经预留好了，换引擎不影响后续环节。

8. **PWA / 离线**
   Service Worker 缓存 pdf.js 资源和 OCR 模型，真正做到断网可用。

9. **MuPDF.js 适配器**
   结构化文本抽取比 pdf.js 强。但它是 AGPL/商业双许可，
   必须放在独立包、独立构建，默认不分发。见 ADR 001。

## 明确不做

- 把 BentoPDF / PDFCraft / pdf2docx 的代码搬进来（AGPL 污染，见 ADR 001）
- 所有页面默认 OCR（慢十倍，收益为负）
- 为了"看起来完整"而输出低置信度的表格
